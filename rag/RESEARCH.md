# Исследовательский протокол КТ-2

В репозитории подготовлен воспроизводимый **пилотный** стенд. Его корпус и разметка созданы для учебного проекта; это не внешний независимо размеченный бенчмарк.

Сохранённые замеры: [BM25, Dense и Hybrid](benchmarks/text/research_report.md),
[текст → изображение](benchmarks/visual_text/research_report.md),
[изображение → изображение](benchmarks/visual_image/research_report.md).
Рядом с каждым отчётом лежат `summary.json` с конфигурацией и `per_query.csv` с результатами по запросам.

## Данные

- `data/wardrobe_seed.json`: точный экспорт 10 исходных вещей фронтенда. Обновление: `node rag/scripts/export_frontend_seed.mjs` из корня репозитория. Экспорт не исправляет исходные признаки незаметно.
- `data/wardrobe_eval.json`: 60 вещей, из них 10 исходных и 50 явно синтетических. По 15 tops/bottoms/shoes, 10 outerwear, 5 accessories. SVG дополнительных вещей — иллюстративные заменители, не фотографии синтетически описанных предметов.
- `data/queries_test.json`: 20 заранее объявленных запросов и наборы допустимых ID по каждому обязательному слоту. Они созданы из описаний до просмотра выдачи моделей.
- `data/queries_dev.json`: 6 отдельных примеров для отладки и выбора гиперпараметров.
- `data/queries_visual_text.json`: 10 текст→изображение smoke-сценариев на исходных SVG.
- `data/queries_visual_image.json`: 10 image→image сценариев на преобразованных растеризациях исходных SVG. PNG подготавливает команда `prepare-visual-queries` CLI; пути в манифесте задаются относительно `rag/`.

Разметка текстового эксперимента имеет статус `assistant_draft_requires_independent_team_review`. Перед использованием цифр в итоговом НИРС команда должна проверить допустимые ID и записать факт проверки в provenance. Нельзя выдавать сгенерированные автором сценарии за независимую экспертную оценку. Изменения разметки после просмотра выдачи требуют нового отдельного теста или явного указания, что исследование исследовательское, а не независимая проверка.

Повторное построение синтетических fixtures: сначала экспорт seed, затем `python rag/data/generate_synthetic.py`. Скрипт не обращается к модели и не корректирует метки по её результатам. Зафиксируйте итоговые JSON до запуска тестового эксперимента.

## Метрики и сравнение

BM25, Dense и Hybrid получают один и тот же corpus snapshot, одинаковые пользовательские и погодные фильтры и одинаковые бюджеты категорий. Основная единица — пара «запрос–слот», в 20 стандартных запросах их 60. В каждом слоте может быть несколько релевантных ID.

`HitRate@K` равен 1, если хотя бы один релевантный ID попал в первые K результатов. `MRR@3` равен обратному рангу первого релевантного ID в первых трёх результатах; при отсутствии попадания равен нулю. В отчёте приведены категории отдельно и macro-average по категориям. Это не Recall@K: попадание одной вещи не означает нахождение всех подходящих вещей. Дополнительно считается доля запросов с попаданием сразу во всех обязательных слотах.

Предметы с `fallback=true` имеют нулевое поисковое свидетельство и исключаются из HitRate/MRR и релевантного покрытия слотов. Они могут заполнить комплект после поиска, но не должны искусственно улучшать retrieval-метрику при отсутствии лексических совпадений. Отдельное `candidate_slot_coverage_with_fallback` показывает только наличие кандидатов для сборки, без утверждения об их релевантности.

Случаи пустого гардероба, отсутствия категории, неизвестного владельца, удаления и повторных ID проверяются инженерными тестами. Пустой ground truth не превращается молча в нулевой HitRate: обычный evaluator отвергает такие метки.

`alpha=0.65` объявлен до теста. Подбор alpha или visual_weight проводится только на dev-наборе; финальные 20 запросов не используются для выбора параметров. Утверждение «Hybrid лучше» допускается только по фактическим результатам. На 20 запросах возможны шум и зависимость от выбранного корпуса; сохраните количество попаданий, не только проценты.

## Визуальная часть

Текстовые embeddings и embeddings изображений хранятся и оцениваются отдельными каналами. Настоящие энкодеры обрабатывают растр SVG; метаданные не подменяют image embeddings. Для visual smoke выбирается режим `visual`, а не `hybrid`, чтобы результат нельзя было объяснить BM25.

Изображения исходного seed стилизованы и могут содержать напечатанные подписи. Семантическая проверка на них ограничена доменом иллюстраций. В каждой категории лишь две вещи, поэтому category HitRate@3 тривиален. Визуальные цифры следует показывать как smoke/instance-проверку и смотреть HitRate@1/MRR, а не заявлять качество поиска по пользовательским фото. Image→image использует преобразованную копию исходного предмета и проверяет устойчивость экземпляра, а не обобщение на новую фотографию.

Для полноценного визуального исследования добавьте реальный каталог с разрешённым использованием фото, независимые запросные снимки, похожие нерелевантные предметы и отдельную разметку. Исходные SVG-результаты нельзя объединять с такой оценкой в одну среднюю цифру без разделения доменов.

### Отдельный пилот на реальных фото

В [`data/photo_pilot/`](data/photo_pilot/) — четыре пальто из коллекции The Met,
для каждого по два отдельных снимка с разных ракурсов. Один кадр индексируется,
второй служит запросом без текста; остальные пальто — нерелевантные кандидаты в том же слоте.
[Происхождение, лицензия CC0 и контрольные суммы](data/photo_pilot/provenance.json).
Это поиск того же экземпляра, а не оценка поиска похожей одежды по фото пользователя.

Из `rag/` с активным Python-окружением проекта и подготовленным кешем моделей:

```bash
run_dir="$(mktemp -d)"
OMP_NUM_THREADS=2 VECLIB_MAXIMUM_THREADS=2 HF_HUB_OFFLINE=1 python -m wardrobe_rag \
  --offline --data-dir "$run_dir/index" --public-root data/photo_pilot \
  --upload-root data/photo_pilot evaluate --dataset data/photo_pilot/queries.json \
  --user photo-pilot --modes visual --repeats 1 --warmup 0 --output results/photo_pilot
```

Смотрите прежде всего HitRate@1 и ранги отдельных запросов. Для `outerwear` движок
возвращает максимум два результата, поэтому HitRate@3 здесь фактически HitRate@2.

В контрольном прогоне `CLIP ViT-B/32` нашёл тот же экземпляр на первом месте в **4 из 4**
запросов (MRR@3 = 1,00). Медиана поиска — 421 мс (CPU, без прогрева, без индексации
и LLM). Для этой малой музейной выборки результат — проверка работы поиска по ракурсам,
а не оценка качества на произвольных фото. Отчёт: [`benchmarks/photo_pilot/`](benchmarks/photo_pilot/).

### Расширенный фотопилот на 12 пальто

Каталог содержит 12 отдельных предметов The Met и 24 музейных фотографии под CC0. Для каждого предмета в индекс идёт снимок спереди, а в запрос — другой снимок сзади. Каждому запросу противостоят 11 других пальто. Несколько предметов похожи по светлому цвету, силуэту и кружевным деталям. [Полная разметка, лицензии и контрольные суммы](data/photo_pilot_expanded/provenance.json).

Из `rag/` с активным Python-окружением и подготовленными весами выполните следующую команду. Для повторного прогона выберите ещё один пустой каталог.

```text
python scripts/benchmark_photo_pairs.py --output results/photo_pilot_expanded_recheck
```

Скрипт проверяет контрольные суммы и отдельные снимки, создаёт новый индекс и использует только режим `visual` с пустой строкой запроса. Бюджет выдачи повышен до 12 исключительно для пилота, чтобы получить полные ранги всех конкурентов. HitRate@1 равен **12/12**. [Полные ранги и разбор пограничных совпадений](benchmarks/photo_pilot_expanded/analysis.md).

## Время и воспроизводимость

Инициализация модели и sync измеряются до вызова evaluator и передаются в metadata. Внутри evaluator выполняются последовательные вызовы, прогрев и повторные замеры. Сохраняются median/p95 и компонентные timings. `first_observed_call_ms` — первый наблюдавшийся вызов в этом процессе; это не доказанный cold start. Для cold-start замера используйте новый процесс, заранее указав, включено ли скачивание весов.

Сохраняются:

- `summary.json`: метрики по категориям, macro/pooled, coverage, времена, происхождение данных, metadata и SHA-256 корпуса/манифеста.
- `per_query.csv`: агрегаты каждого запроса, слота и режима.
- `measurements.csv`: все повторения; это повторные измерения, не новые независимые запросы.
- `raw_rankings.jsonl`: вход, кандидаты, scores и timings каждого запуска.
- `research_report.md`: таблица для отчёта с явными ограничениями.

Сравнение latency выполняется на одном устройстве и одном способе прогрева. Скорость retrieval не включает LLM, SSE или браузер. Время первого токена и время провалидированного аутфита измеряет будущий backend отдельно. В metadata должны присутствовать модель/revision, устройство, число вещей, конфигурация поиска, версия кода и время sync. Не заменяйте реальные замеры статическими процентами админки или случайным matchScore.
