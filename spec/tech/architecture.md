# Архитектура фронтенда и контракт интеграции

Для точечной правки гардеробный модуль предоставляет `RAGService.retrieve_slot(SlotSearchRequest)` и возвращает `SlotSearchResult`. Результат содержит кандидатов одного слота, ID оставшихся вещей, ID заменяемой вещи и ревизию гардероба. Пустой список означает отсутствие подходящей альтернативы. HTTP-запрос, выбор последней карточки, история и сборка ответа остаются у backend. См. [контракт и пример](../../rag/INTEGRATION.md#поиск-для-одной-правки-готового-образа).

## Режим КТ-2 по учебным документам

`app.kt2_api:app` запускается отдельно, не использует гардероб пользователя или историю.
`GET /kt2` отдаёт форму, `POST /api/kt2/ask` принимает `{ "question": "…" }`.
При старте сервер индексирует заголовки и тексты из `backend/kt2_data/corpus.json`.
Обратный индекс хранит `слово → {ID: частота}`; длины документов и IDF вычисляются один раз.
BM25 (`k1=1.2`, `b=0.75`) обходит списки документов только для уникальных слов запроса.
Русские словоформы нормализует Snowball; числа и токены с латиницей не стеммируются.
До трёх результатов передаются Qwen. Каждый фрагмент ответа содержит ID источника;
схема ограничивает ID найденными документами, а сервер повторно проверяет принадлежность
и формирует ссылки. API возвращает `answer`, `refused`, `sources`, `hits`, `model`.
`sources` — процитированные документы, `hits` — ранжированная выдача; каждый элемент
содержит `id`, `title`, `text`, `score`. Пустая выдача или пустой список фрагментов означает
`refused: true`. Ошибка модели — HTTP 502, не отказ. `askStylist` и типы React не меняются.

## Реализованный backend КТ-2 (22 ноября 2026)

В `backend/` находится FastAPI-сервер — связующее звено между React-приложением, пакетом
поиска `wardrobe_rag` и языковой моделью. Запуск, переменные окружения и полное описание
API: [backend/README.md](../../backend/README.md).

```
React SPA (src/services/stylistApi.ts)
        │  POST /api/recommend-outfit  { query, wardrobe, wardrobe_ids, user_id, context }
        ▼
FastAPI backend/app
  1. sync              — снимок гардероба → wardrobe_rag (Chroma, BM25, эмбеддинги)
  2. filter/retrieve   — ограничения повода и погоды, кандидаты по слотам
  3. LLM               — OpenAI-совместимый клиент (Qwen / Llama / GPT-4o), JSON с ID вещей
  4. validate_selection — проверка выбранных id пакетом поиска
  5. repair / fallback — повтор LLM с причинами отказа, затем детерминированная сборка
        │
        ▼
  { text, suggestedOutfit, referencedItemIds, source, missingSlots, warnings, timings, meta }
```

Ключевые решения:

- **Один чат, две ветки.** На вопросы о стиле Qwen отвечает с учётом истории, без
  синхронизации гардероба, поиска и карточки. При подборе из гардероба действует
  цепочка выше. Распознаваемые короткие уточнения к последней карточке запускают
  новый поиск по текущему снимку гардероба.

- **Модель выбирает ID.** Сервер подставляет проверенные `WardrobeItem` и из этих же
  данных строит текст и карточку. В подборе свободный текст модели не показывается.
- **Двойная проверка.** Форма JSON проверяется Pydantic-схемой, состав образа —
  `RAGService.validate_selection` (чужие id, повторы, лимиты слотов, обязательные слоты,
  якорная вещь, изменившаяся ревизия гардероба).
- **Неполный комплект не выдаётся за образ.** При непустом `missing_slots` LLM не вызывается:
  клиент получает текст с объяснением и `missingSlots`, без `suggestedOutfit`.
- **Фильтр до ранжирования.** Для пляжа используются признаки пляжной одежды и
  открытой обуви; общие погодные ограничения опираются на сезон и явные атрибуты.
  Правило работает в продуктовой цепочке, не меняя экспериментальные прогоны RAG.
- **Источник ответа явный.** `source`: `llm` | `mock` | `fallback` | `none`. Сбой LLM не даёт
  HTTP 500, а превращается в `fallback` с предупреждением.
- **Поиск подключён как библиотека**, а не по HTTP: модели и Chroma создаются один раз при
  старте, блокирующие вызовы выполняются в пуле потоков. Если пакет или кеш моделей
  недоступны, включается запасной встроенный BM25 — он помечается в `/health`,
  `meta.retriever` и `warnings`. На показе задаётся `RAG_ENGINE=wardrobe_rag`, и тогда сервер
  без настоящего поиска просто не стартует.
- **`user_id` — демо-идентификатор** из тела запроса (id текущего пользователя фронтенда),
  не защищённая сессия. Авторизации на сервере нет.
- **`matchScore`** — прозрачная эвристика (полнота слотов, позиция в выдаче, поисковые
  свидетельства, палитра), а не вероятность. Формула приходит в `meta.matchScoreMethod`.
- **Капсула и корпус исследования разделены.** `GET /api/wardrobe/base-capsule`
  отдаёт исходные 10 вещей и 40 дополнительных из общего с фронтендом
  `rag/data/wardrobe_capsule_extra.json`. Подкатегории — фильтры по `tags`;
  пять слотов подбора, исходный seed и исследовательские фикстуры не меняются.

## Реализованный модуль поиска КТ-2 (19 ноября 2026)

В `rag/` находится независимый Python-пакет `wardrobe_rag`. Он реализует постоянный
индекс Chroma, BM25, текстовые и визуальные эмбеддинги, RRF, кандидатов по слотам,
проверку выбранных ID и исследовательский runner. FastAPI и LLM остаются следующим
этапом интеграции. Команда `demo` поднимает отдельный локальный инженерный стенд с
настоящим поиском и вкладом каждого канала; генерации LLM в этом стенде нет.

Полный актуальный Python-контракт и пример подключения: [rag/INTEGRATION.md](../../rag/INTEGRATION.md).
JSON Schema экспортируется `python -m wardrobe_rag export-schemas`.
TypeScript-типы `RetrievalResult`/`RetrievalCandidate` отражают диагностический ответ.
У `WardrobeItem` добавлены необязательные `imagePath` и `weather`; текущий UI и seed
продолжают работать без них. Погодные поля — явно размеченные факты, `null` означает
неизвестное свойство. `embeddingSnippet` не заменяет актуальные атрибуты при индексации.

Поиску передаётся серверный `user_id`, полный снимок вещей и запрос. Один и тот же
`item.id` у разных пользователей изолирован. Изменения и удаление синхронизируются
полным снимком; `wardrobe_revision` позволяет отклонить устаревший выбор после LLM.
Результат содержит `candidates_by_slot`, `required_slots`, `missing_slots`,
`timings_ms`, `model_fingerprint`, `alpha`, `visual_weight`, исходные расстояния,
ранги и вклады RRF. Неранжированные резервные кандидаты помечаются `fallback=true`
и исключаются из HitRate/MRR. `score` не является процентом совместимости.

Раздел 3 ниже описывает контракт REST API так, как он реализован в `backend/`. В ответе
`items` содержат полные канонические `WardrobeItem`, а `referencedItemIds` совпадают с
выбранными ID. Сигнатура `askStylist` сохранена. Фронтенд по умолчанию работает на
клиентском симуляторе; настоящий сервер включается переменной `VITE_USE_REAL_BACKEND=true`.

## 2. Модель данных (Types)

### Элемент гардероба (`WardrobeItem`)
```typescript
interface WardrobeItem {
  id: string;
  title: string;
  category: 'tops' | 'bottoms' | 'outerwear' | 'shoes' | 'accessories';
  color: string;
  season: 'all' | 'spring/summer' | 'autumn/winter';
  style: string[];
  tags: string[];
  imageUrl: string;
  brand?: string;
  material?: string;
  embeddingSnippet?: string;
  uploadedAt: string;
}
```

### Образ аутфита (`OutfitLook`)
```typescript
interface OutfitLook {
  id: string;
  title: string;
  description: string;
  occasion: string;
  items: WardrobeItem[];
  stylistReasoning: string;
  matchScore: number; // e.g. 96
  confidenceTips: string[];
}
```

### Название диалога (`ChatThread`)

Опциональное поле `autoTitlePending` сохраняется вместе с диалогом в браузере. Значение
`true` позволяет взять название из `suggestedOutfit.title` первого готового подбора.
После этого либо после ручного переименования поле получает `false`. Диалоги без этого поля
сохраняют своё название. Дополнительного запроса к серверу нет.

## 3. Контракт REST API (реализован в `backend/`)

### Эндпоинт: `POST /api/recommend-outfit`
**Запрос (Request body):**
```json
{
  "query": "Подбери образ для деловой встречи",
  "wardrobe": [{ "id": "item-1", "title": "Белая хлопковая рубашка оверсайз", "category": "tops", "...": "..." }],
  "wardrobe_ids": ["item-1", "item-2", "item-3", "item-4"],
  "user_id": "user-elena",
  "context": {
    "occasion": "business",
    "weather": "rainy",
    "vibe": "minimalism"
  }
}
```

- `query` — единственное обязательное поле.
- `wardrobe` — полный снимок вещей пользователя (гардероб хранится в `localStorage`, поэтому
  фронтенд присылает его целиком). Сервер синхронизирует снимок с индексом и ищет только по нему.
  Повторная отправка того же снимка не вызывает переиндексацию.
- `wardrobe_ids` без `wardrobe` (исходный контракт КТ-1) — поиск по ранее синхронизированному
  снимку пользователя, ограниченный этими id.
- `history` — предыдущие реплики этого диалога (`sender`, `text`, `hasOutfit`, `itemIds`).
  `itemIds` — ID вещей карточки этого ответа: по ним сервер меняет одну или несколько названных
  вещей последнего образа, не восстанавливая состав по названиям. Фронтенд
  отправляет до 12 реплик, а в промпт модели попадают последние 6. `hasOutfit` — подсказка
  для маршрутизации уточнения, не источник доверенных ID.
- Другие необязательные поля: `anchor_item_id`, `mode`, `alpha`, `visual_weight`, `query_image`,
  `debug` (диагностика поиска).

**Ответ (Response 200 OK):**
```json
{
  "text": "Для деловой встречи я подобрал сбалансированный смарт-кэжуал комплект...",
  "suggestedOutfit": {
    "id": "outfit-3f2a9c41d0b7",
    "title": "Деловой минимализм",
    "description": "Строгий, но комфортный образ со структурированным блейзером",
    "occasion": "Деловая встреча",
    "items": [
      {
        "id": "item-2",
        "title": "Черный структурированный блейзер",
        "category": "outerwear",
        "color": "Черный",
        "season": "all",
        "style": ["business", "smart-casual", "chic"],
        "tags": ["жакет", "блейзер"],
        "imageUrl": "/clothes/blazer.svg",
        "uploadedAt": "2026-10-02"
      }
    ],
    "stylistReasoning": "Контраст черного верха со светлым низом балансирует строгие пропорции.",
    "matchScore": 87,
    "confidenceTips": [
      "Заправьте рубашку в брюки для создания вертикали силуэта."
    ]
  },
  "referencedItemIds": ["item-2", "item-1", "item-4", "item-8"],

  "source": "llm",
  "missingSlots": [],
  "warnings": [],
  "timings": { "syncMs": 12.1, "retrievalMs": 48.0, "llmMs": 1830.5, "totalMs": 1902.3 },
  "meta": {
    "llmProvider": "openai",
    "llmModel": "qwen/qwen3.8-27b:free",
    "llmAttempts": 1,
    "retriever": "wardrobe_rag",
    "wardrobeRevision": "…",
    "occasion": "Деловая встреча",
    "matchScoreMethod": "эвристика: …; не вероятность"
  }
}
```

Поля `text`, `suggestedOutfit`, `referencedItemIds` — исходный контракт КТ-1. Остальные поля
добавочные, клиент может их игнорировать:

| Поле | Значение |
|---|---|
| `source` | `llm` — ответ модели; `mock` — демопровайдер; `fallback` — запасной ответ; `rules` — правка образа, где модели выбирать было не из чего; `none` — подбор остановлен до генерации |
| `edit` | Только если карточка получена из прошлой: `operation` (`add`, `replace`, `remove`, `restyle`), `slot`, `baseItemIds`, `keptItemIds`, `addedItemIds`, `removedItemIds` |
| `missingSlots` | Категории, которых не хватает для законченного образа. Если список непуст, `suggestedOutfit` отсутствует |
| `warnings` | Диагностика синхронизации, поиска и фолбэков |
| `timings` | Миллисекунды по этапам; для потокового совета дополнительно `llmFirstTextMs` |
| `meta` | Провайдер, модель и число попыток; `retriever` и ревизия относятся к подбору, а не к обычному разговору |
| `retrieval` | Только при `debug: true`: `RetrievalResult` (см. `rag/contracts`) с полем `engine` |

`material_weather_score` в диагностике кандидата — отдельная подсказка для ранжирования
и сборки при известной погоде. Она учитывает заявленный утеплитель и тёплые волокна
в основном материале одежды или в подкладке. `score` и вклады BM25/Dense/Visual не меняются.
Подсказка не записывается в карточку и не отменяет ограничения по размеченной температуре
или влагозащите. Бэкенд передаёт её модели как `materialWeatherScore`, а не как факт о вещи.

Ошибки: `422` — некорректное тело запроса; `503` — поисковый движок не смог обработать запрос
(например, гардероб изменился во время генерации).

### Эндпоинт: `POST /api/recommend-outfit/stream` (SSE)

То же тело запроса, ответ — `text/event-stream`. В подборе после `status` и
`retrieval` идёт генерация ID и проверка. Затем приходят `delta` с готовым текстом
из проверенных вещей и `result` с полной карточкой; при ошибке — `error`.
Неподтверждённый текст подбора не отправляется.
Без поиска по гардеробу поток содержит `status` (`generation`), `delta` и `result`,
а `meta.retriever` в ответе отсутствует.

В режиме `VITE_USE_REAL_BACKEND=true` чат использует этот эндпоинт. Черновик показывается
только в своём диалоге, не сохраняется в истории и заменяется событием `result`.
При удалении диалога или выходе запрос отменяется; при обрыве потока автономный ответ
явно помечается как локальная симуляция.

### Эндпоинт: `POST /api/wardrobe/recognize`

Тело — байты JPEG, PNG или WebP до 10 МиБ; `Content-Type` соответствует файлу. Для распознавания
браузер отправляет JPEG до 1600 px по длинной стороне, а для карточки оставляет отдельное сжатое
превью. Снимок с текстом не сохраняется. `wardrobe_rag` предлагает название, категорию и цвет
через CLIP. Tesseract считывает текст; локальная модель извлекает характеристики из обычного
описания товара, а без неё остаётся разбор явных характеристик и фраз о цвете. Для распознанной
вещи цвет по фото — вариант с максимальной оценкой CLIP. Из читаемого названия категория
определяется по однозначному типу, а не отдельному ответу LLM. OCR заменяет визуальное
название и категорию только парой; ручной выбор категории приоритетен. Числовые коды цвета
без названия не интерпретируются. `?label_only=true` пропускает CLIP — для бирки или скриншота.
Подсказка `season` появляется только из явной однозначной строки вида «Сезон: Весна / лето»,
не из изображения, типа вещи или утеплителя. При противоречии подсказок сезон не заполняется;
ручной выбор, в том числе «Не указан», приоритетен.
`material` хранит состав основного полотна или верха. В необязательном `materialDetails`
сохраняются отдельно подкладка (`lining`), утеплитель (`insulation`), подошва (`sole`), стелька
(`insole`) и отделка (`trim`). Читаемые доли сохраняются без округления; неоднозначные секции
не дополняются догадками. RAG индексирует эти поля из сохранённой вещи, а не сырой OCR.
Пример: `{"suggestion":{"material":"100% хлопок","materialDetails":{"lining":"100% вискоза"}}}`.
Каждое поле может быть `null`; `suggestion: null` означает отсутствие подсказок. `413` — слишком большой
файл, `422` — неподдерживаемое или повреждённое изображение, `503` — модель недоступна. Загрузки
не отправляются внешним сервисам и не индексируются. Ручные правки приоритетны, вещь сохраняется только по кнопке.

### Эндпоинт: `POST /api/wardrobe/sync`

```json
{ "user_id": "user-elena", "items": [ { "id": "item-1", "...": "..." } ] }
```

Полный снимок гардероба: повтор идемпотентен, отсутствующие вещи удаляются из индекса, пустой
массив очищает гардероб только этого пользователя. Ответ — `SyncResult` пакета поиска
(`revision`, `indexed_count`, `image_count`, `added_count`, `updated_count`, `deleted_count`,
`unchanged_count`, `warnings`, `timings_ms`). `GET /api/wardrobe?user_id=…` возвращает текущий снимок.
Отсутствующий сезон сохраняется как `unknown`: в поисковый текст и факты для стилиста он не
попадает. `all` — отдельное значение «Всесезонно». Существующие значения не переписываются.

### Эндпоинты куратора: `GET` / `PUT /api/admin/settings`

Панель куратора получает режим поиска (`mode`), веса (`alpha`, `visualWeight`),
`temperature` и `personaPrompt` с сервера. Модель и движок отображаются без возможности
подмены из браузера. При записи куратор вводит токен, который передаётся в `X-Admin-Token`
и должен совпадать с `ADMIN_TOKEN` сервера. Токен не сохраняется в браузерном хранилище.
