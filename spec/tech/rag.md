# RAG-пайплайн КТ-2: мультимодальный поиск и слоты

Реализация находится в `rag/` и поставляется как Python-пакет `wardrobe_rag`. FastAPI, LLM и SSE подключаются отдельно. Запуск — `rag/README.md`, контракт backend — `rag/INTEGRATION.md`, исследовательский протокол — `rag/RESEARCH.md`.

## Индексация

`sync(user_id, items)` принимает полный снимок личного гардероба. Канонический документ строится из актуальных title/category/color/material/season/brand/style/tags. Устаревший embeddingSnippet не индексируется. Владельцем ограничены поиск и операции изменения; ключ предмета включает user_id и item_id.

Текстовые эмбеддинги кодируются `sentence-transformers/paraphrase-multilingual-mpnet-base-v2`. Изображения — `sentence-transformers/clip-ViT-B-32`; русские запросы к изображениям — выровненной с ним `clip-ViT-B-32-multilingual-v1`. MPNet и CLIP хранятся в отдельных Chroma-коллекциях с cosine distance. Их векторы напрямую не складываются.

Картинки принимаются из ограниченных public/upload каталогов и image Data URL. Стартовые SVG растеризуются. Сетевые URL и внешние ресурсы SVG не загружаются. Отсутствие изображения фиксируется явно.

Повторный snapshot не создаёт дубликаты; изменения переиндексируются, удалённые вещи исчезают из всех каналов. Изменение модели или формата документа учитывается в fingerprint. Снимки остальных пользователей сохраняются.

## Ранжирование

Доступны режимы `bm25`, `dense`, `hybrid`, `visual`, `multimodal`. BM25 одинаково обрабатывает документы и запросы: регистр, ё/е, русская морфология и нормализация атрибутов.

В `hybrid` применяется weighted Reciprocal Rank Fusion:

```text
score(d) = alpha / (c + rank_dense(d))
         + (1 - alpha) / (c + rank_bm25(d))
```

Ранги начинаются с 1; отсутствующий результат имеет нулевой вклад. Исходно alpha=0.65, c=60. Это параметры эксперимента, а не гарантированно оптимальные значения. Raw BM25 и cosine distance не суммируются.

`visual` выполняет текст → изображения или изображение → изображения. В `multimodal` веса каналов: BM25=`1-alpha`, semantic=`alpha*(1-visual_weight)`, visual=`alpha*visual_weight`. При недоступности одного Dense-канала вес перераспределяется внутри Dense-группы; диагностика сообщает это явно.

Фильтры пользователя и категории применяются до короткого списка. Бюджеты: tops≤3, bottoms≤3, shoes≤3, outerwear≤2, accessories≤2. Глобальный Top-K не заменяет независимый поиск слотов.

Если слот содержит допустимые вещи без retrieval-свидетельств, они могут включаться как `fallback=true`, score=0, ranks=None. Это помогает обеспечить категории комплекта, но не выдаётся за совпадение поиска. Такие кандидаты исключаются из HitRate/MRR и учитываются отдельной метрикой покрытия категорий.

## Ограничения и ответ

Обязательные слоты: tops, bottoms, shoes. Верхняя одежда может стать обязательной по явному погодному контексту. Структурированный weather задаёт температуру, водостойкость, защиту от ветра и открытую обувь. Неизвестное значение не превращается в погодную гарантию; потребитель получает предупреждения.

Первая версия выбирает один предмет каждого основного слота, поддерживает anchor_item_id и исключения. Нехватка категории возвращается в missing_slots. Предметы из демонстрационной капсулы или чужого пользователя не подставляются. Детерминированная сборка перебирает сочетания кандидатов с небольшой прозрачной эвристикой цветовых акцентов; правило 60-30-10 по площади изображения не заявляется.

LLM получает найденных кандидатов и возвращает выбранные ID. `validate_selection` проверяет принадлежность разрешённому набору, уникальность, категории, обязательные слоты и якорную вещь. Сервис проверяет revision гардероба. Backend подставляет канонические вещи и валидирует внешний OutfitLook через Pydantic.

Результат поиска содержит candidates_by_slot, required_slots/missing_slots, warnings, timings_ms, модельный fingerprint, revision и параметры fusion. Кандидаты содержат raw scores/distances, ранги и отдельные вклады. Retrieval score не является процентом гармонии или вероятностью качества ответа.

## Исследование и демонстрация

BM25, Dense и Hybrid сравниваются на одном корпусе, одинаковых фильтрах и Top-K. Тест: 20 запросов с релевантными ID по слотам; dev-примеры отделены. Метрики: HitRate@K, MRR@K по категориям и macro-average; дополнительно релевантное покрытие всех обязательных слотов. Индексация, холодная загрузка, прогретый retrieval и LLM latency измеряются раздельно.

Исходная капсула содержит две вещи на категорию, поэтому HitRate@3 на ней вырожден. Расширенный явно синтетический корпус предназначен для пилотного текстового эксперимента. Повторные SVG не образуют независимый визуальный benchmark. Работа image pipeline на иллюстрациях не доказывает качество на фотографиях; это ограничение сохраняется в отчёте.

Отдельная инженерная demo-панель может показывать реальные кандидаты, веса, вклады и визуальный запрос. Она не заменяет общий Live UI → LLM, для которого ещё нужны backend и клиентская интеграция.
