# Backend AI-стилиста — часть Егора, КТ-2

FastAPI-сервер, который связывает фронтенд, поиск по гардеробу (`rag/`, пакет `wardrobe_rag`) и языковую модель:

```
React SPA ──POST /api/recommend-outfit──▶ FastAPI (backend/)
                                           │ 1. синхронизация гардероба   ─▶ wardrobe_rag.sync
                                           │ 2. фильтр повода и погоды, затем поиск по слотам
                                           │ 3. LLM выбирает ID (Qwen / OpenAI-совместимая модель)
                                           │ 4. проверка выбора           ─▶ wardrobe_rag.validate_selection
                                           │ 5. при ошибке — повтор LLM, затем детерминированная сборка
                                           ▼
                              { text, suggestedOutfit, referencedItemIds, source, … }
```

Что гарантирует сервер:

- В образ попадают **только реальные вещи пользователя**: модель возвращает id, полные объекты подставляет сервер, а выбор проверяет пакет поиска (чужие и выдуманные id, две пары обуви, пропущенный обязательный слот, якорная вещь, устаревшая ревизия гардероба).
- **Неполный комплект не выдаётся за образ.** Если нет обуви или при −5 °C нет верхней одежды, приходит текст с объяснением и `missingSlots`, без карточки.
- **Описание совпадает с карточкой.** Сервер строит оба из проверенных вещей. Для явного пляжного запроса закрытая обувь не становится кандидатом, даже если другой обуви нет. Погодные ограничения учитывают указанные свойства вещей; неизвестные свойства не подтверждены.
- **Источник ответа виден**: `source` = `llm` (настоящая модель), `mock`, `fallback` (модель недоступна или не прошла проверку — образ собран детерминированно) или `none` (образа нет).
- На корректный запрос сервер не отвечает 500 из-за LLM: сбой модели превращается в `fallback`.

## Запуск

Нужен Python 3.11–3.14 (как у `rag/`). Команды выполняются из каталога `backend/`.

**macOS / Linux**

```bash
cd backend
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python -m pip install -e ../rag          # поиск: Chroma, sentence-transformers, torch
.venv/bin/python -m uvicorn app.main:app --port 8000
```

**Windows (PowerShell)**

```powershell
cd backend
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m pip install -e ..\rag
.\.venv\Scripts\python.exe -m uvicorn app.main:app --port 8000
```

Проверка: <http://localhost:8000/health>, интерактивная документация — <http://localhost:8000/docs>.

```bash
curl -s -X POST http://localhost:8000/api/recommend-outfit \
  -H "Content-Type: application/json" \
  -d '{"query": "Москва: +6°C, ветрено, деловая встреча"}'
```

На чистом сервере запрос с одним `query` использует гардероб `demo` из 50 вещей.
`SEED_WARDROBE_PATH` позволяет выбрать другую фикстуру; существующий снимок `demo` автоматически не перезаписывается.

Без `pip install -e ../rag` сервер тоже запустится — на встроенном лексическом поиске `builtin-bm25`. Это запасной режим для разработки фронтенда; он помечается в `/health`, в `meta.retriever` и в `warnings` каждого ответа.

### Модели поиска

Первый запуск с `wardrobe_rag` скачивает около 2,3 ГБ весов. Сделайте это заранее (подробности — в [`rag/README.md`](../rag/README.md)):

```bash
cd ../rag
python -m wardrobe_rag --cache-dir .model_cache --public-root ../public init-models
```

После этого в `backend/.env` можно поставить `RAG_OFFLINE=true` — модели берутся только из кеша. Сервер грузит модели на старте: до первого запроса может пройти несколько десятков секунд, зато сам первый запрос не тормозит.

### Подключение Qwen

Скопируйте `.env.example` в `.env` и раскомментируйте один из блоков:

| Вариант | Настройки | Когда выбирать |
|---|---|---|
| OpenRouter | `LLM_PROVIDER=openai`, `LLM_BASE_URL=https://openrouter.ai/api/v1`, `LLM_MODEL=qwen/qwen3.8-27b:free`, `LLM_API_KEY=…` | Быстро и без нагрузки на ноутбук; нужен интернет |
| Ollama | `LLM_PROVIDER=openai`, `LLM_BASE_URL=http://localhost:11434/v1`, `LLM_MODEL=qwen3:8b`, `LLM_API_KEY=ollama` | Полностью офлайн; на CPU отвечает медленнее |

Клиент один — OpenAI-совместимый `/chat/completions`, поэтому Llama, GPT-4o и другие модели подключаются теми же тремя переменными. Если провайдер не поддерживает `response_format`, поставьте `LLM_JSON_MODE=false`: JSON всё равно требуется промптом, разбирается терпимо (markdown-ограждения, `<think>`-блоки reasoning-моделей) и проверяется.

### Подключение фронтенда

В корне репозитория создайте `.env.local`:

```
VITE_USE_REAL_BACKEND=true
VITE_BACKEND_URL=http://localhost:8000
```

и перезапустите `npm run dev`. Чат отправляет запрос на `/api/recommend-outfit/stream`:
советы о стиле приходят по мере генерации, а текст подбора и карточка — после проверки состава.
Приветствия и вопросы о стиле обрабатывает та же LLM без поиска по гардеробу и без карточки.
Для подбора из гардероба используется RAG. «А можно потеплее?» после карточки уточняет
температуру или предлагает точечное утепление, сохраняя выбранную вещь.
Без этого файла фронтенд работает на клиентском симуляторе. Если поток недоступен
или оборвался, фронтенд помечает запасной ответ как симуляцию.

Панель куратора читает настройки с сервера. Чтобы сохранить изменения, задайте
`ADMIN_TOKEN` в `backend/.env` и введите тот же токен в панели. Без токена на сервере
настройки доступны только для чтения.

## API

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/api/recommend-outfit` | Подобрать образ (контракт КТ-1 + добавочные поля) |
| `POST` | `/api/recommend-outfit/stream` | То же потоком SSE |
| `POST` | `/api/wardrobe/sync` | Заменить гардероб пользователя полным снимком, вернуть `SyncResult` |
| `GET` | `/api/wardrobe?user_id=` | Текущий снимок гардероба на сервере |
| `GET` | `/api/wardrobe/base-capsule` | Демо-капсула из 50 вещей, независимо от снимка `demo` |
| `POST` | `/api/wardrobe/recognize` | Подсказки по фото вещи или бирки (локальные CLIP и OCR) |
| `GET` / `PUT` | `/api/admin/settings` | Режим поиска, α, β, температура, персона стилиста |
| `GET` | `/health` | Состояние, LLM и движок поиска |

Передавайте до 10 МиБ байтов изображения с `Content-Type: image/jpeg`, `image/png` или `image/webp`.
Движок `wardrobe_rag` использует CLIP для названия, категории и цвета. Для чтения бирки или карточки товара нужны
читаемый текст и локальный `tesseract` в `PATH` (например, `brew install tesseract`, языковые
пакеты `eng` и/или `rus`; на macOS дополнительные языки даёт `brew install tesseract-lang`).
`material` хранит основной материал, а `materialDetails` — прочитанные составы отдельных частей
(`lining`, `insulation`, `sole`, `insole`, `trim`), включая дробные проценты. Характеристики можно
исправить вручную; сырой OCR в поисковый индекс не передаётся.
Для распознанной вещи CLIP предлагает цвет с максимальной оценкой, даже если другие оттенки получили близкие оценки.
После OCR описание товара разбирает локальная LLM, если `LLM_PROVIDER=openai` и `LLM_BASE_URL`
указывает на loopback-адрес (например, Ollama). Внешнему LLM текст не отправляется. Без локальной
модели остаётся разбор явных характеристик и фраз о цвете. Если текст не читается, работают
визуальные подсказки. `?label_only=true` извлекает данные только из текста и не требует CLIP.
Каждое поле может быть `null`; отсутствие всех подсказок — `{"suggestion":null}`.
Распознавание фото вещи без CLIP отвечает `503`, ручное добавление остаётся доступным.

### Запрос рекомендации

```jsonc
{
  "query": "Подбери образ для деловой встречи",   // обязательно
  "wardrobe": [ /* полные WardrobeItem */ ],       // снимок гардероба: синхронизируется и используется
  "wardrobe_ids": ["item-1", "item-2"],            // или только id — поиск по уже синхронизированному снимку
  "user_id": "user-elena",                         // по умолчанию "demo"
  "context": { "occasion": "business", "weather": "rainy", "vibe": "minimalism" },
  "history": [                                     // последние реплики диалога
    { "sender": "user", "text": "Подбери образ в офис." },
    { "sender": "assistant", "text": "…", "hasOutfit": true,
      "itemIds": ["item-1", "item-4", "item-42"] }  // ID вещей карточки — для точечной правки
  ],
  "anchor_item_id": "item-10",                     // образ вокруг вещи (иначе вещь ищется по названию в query)
  "mode": "multimodal", "alpha": 0.65, "visual_weight": 0.35,  // параметры поиска для панели защиты
  "debug": true                                    // вернуть полную диагностику поиска в поле retrieval
}
```

`user_id` — демо-идентификатор из тела запроса, **не защищённая сессия**: авторизации в учебном проекте нет.

### Ответ

```jsonc
{
  "text": "Собрал лаконичный деловой образ…",
  "suggestedOutfit": {                 // отсутствует, если образа нет
    "id": "outfit-3f2a…", "title": "…", "description": "…", "occasion": "…",
    "items": [ /* полные WardrobeItem из гардероба */ ],
    "stylistReasoning": "…", "matchScore": 87, "confidenceTips": ["…"]
  },
  "referencedItemIds": ["item-2", "item-1", "item-4", "item-8"],

  "source": "llm",                     // llm | mock | fallback | none
  "missingSlots": [],                  // чего не хватает для законченного образа
  "warnings": ["…"],                   // диагностика поиска, синхронизации и фолбэков
  "timings": { "syncMs": 12.1, "retrievalMs": 48.0, "llmFirstTextMs": 410.2, "llmMs": 1830.5, "totalMs": 1902.3 },
  "meta": { "llmProvider": "openai", "llmModel": "qwen/…", "llmAttempts": 1, "retriever": "wardrobe_rag",
            "wardrobeRevision": "…", "occasion": "Деловой выход", "matchScoreMethod": "эвристика: …" },
  "retrieval": { /* только при debug=true: RetrievalResult из rag/contracts + поле engine */ }
}
```

`matchScore` нужен карточке образа на фронтенде. Это **не вероятность и не оценка модели**: прозрачная эвристика из полноты обязательных слотов, позиции выбранных вещей в поисковой выдаче, доли вещей с поисковыми свидетельствами и сдержанности палитры. Формула возвращается в `meta.matchScoreMethod`.

### Поток SSE

`POST /api/recommend-outfit/stream` принимает то же тело и отдаёт `text/event-stream`:

| Событие | Данные | Когда |
|---|---|---|
| `status` | `{"stage": "retrieval" \| "generation" \| "validation"}` | Смена этапа |
| `retrieval` | Сводка поиска (при `debug` — полная диагностика) | До первого текста |
| `delta` | `{"text": "фрагмент"}` | Чанки LLM для совета; для подбора — только проверенный текст |
| `result` | Полный ответ, как у обычного эндпоинта | Последним; его `text` заменяет накопленные дельты |
| `error` | `{"message": "…"}` | Если поиск не смог обработать запрос |

`timings.llmFirstTextMs` относится к свободному диалогу. При подборе сервер сначала
получает и проверяет ID, затем публикует текст из выбранных вещей, не показывая черновик модели.

Состав остаётся на карточке; чат даёт короткий комментарий о пропорциях, цвете или
стилизации. При −15 °C и ниже сервер не предлагает обувь или верхнюю одежду без
нижней границы температуры, подходящей под запрос. Если подходящей вещи нет,
карточка не показывается.

## Правка последнего образа

После карточки пользователь может попросить изменить в ней одну или несколько вещей. Фронтенд присылает в
`history` у ответа с карточкой поле `itemIds`, и сервер работает с этими ID, а не восстанавливает
состав по названиям. Что происходит с репликой:

| Реплика | Что делает сервер |
|---|---|
| «А можешь добавить какую-нибудь куртку, если похолодает?» | Ищет верхний слой к тем же вещам (`retrieve_slot`), показывает новую карточку: прежние ID сохранены, добавлен один |
| «Замени туфли на что-нибудь без каблука, остальное оставь» | Меняет ровно одну вещь; прежняя пара в кандидаты не попадает. Нет подходящей — объясняет и новой карточки не показывает |
| «Не хочу футболку» | Заменяет футболку вещью другого типа и не предлагает футболки снова при правке этого образа, пока пользователь сам не попросит вернуть этот тип |
| «Замени верх и низ» или «верх и низ» сразу после уточняющего вопроса | Подбирает обе вещи через `retrieve_slot` и публикует одну карточку только при успехе обеих замен. Остальные ID сохраняются |
| «Без сумки, пожалуйста» | Убирает необязательную вещь. На просьбу убрать единственную обувь спрашивает, нужна ли замена |
| «А можно потеплее?» | Сохраняет выбранную вещь, текущую верхнюю одежду и обувь. Уточняет температуру, если неизвестна. Добавляет внешний слой или предлагает обоснованно более тёплую вещь; если подходящей правки нет, карточку не меняет |
| «Мне в этом будет комфортно?» | Даёт практический совет по последнему образу или уточняет температуру для вопроса о жаре и холоде. Карточка не меняется, модель не вызывается (`source: "rules"`) |
| «Рубашка со штанами сочетается?» | Называет вещи последней карточки и объясняет сочетание по цвету или стилю. Состав не меняется; модель не вызывается |
| «Зачем шорты? Холодно» | Если в карточке шорты, ищет только длинный низ и сохраняет остальной состав. Если подходящего низа нет, новой карточки нет |
| «Верни предыдущий образ» | Восстанавливает состав предпоследней карточки по ID из истории, без поиска и вызова модели; после удаления вещи не подставляет замену |
| «Замени вот это» | Задаёт один уточняющий вопрос, модель не вызывается |
| «С чем носить чёрные ботинки на день рождения?» после диалога про пляж | Самостоятельный вопрос уходит модели без истории: пляж не наследуется. С «…из моего гардероба» — новый подбор со своим поводом |

Вид реплики определяется правилами (`app/services/followup.py`), а не моделью: это проверяется
тестами и не добавляет вызов LLM. Модель нужна только чтобы выбрать одну вещь из нескольких
кандидатов поиска. Перед показом сервер проверяет состав (слоты, обязательные категории) и
ревизию гардероба. Если вещь прошлого образа уже удалена из гардероба, правка не выполняется, а
пользователь получает объяснение.

В ответе на правку есть поле `edit` — по нему правку можно проверить автоматически:

```jsonc
"edit": { "operation": "replace", "slot": "shoes",
          "baseItemIds": ["item-1", "item-4", "item-42"],   // прошлая карточка
          "keptItemIds": ["item-1", "item-4"], "addedItemIds": ["item-36"], "removedItemIds": ["item-42"] }
```

`operation: "restyle"` описывает в том числе атомарную замену нескольких вещей; поле `slot` в этом случае не передаётся.
`source` у правки: `llm` — модель участвовала в выборе; `rules` — сервер выбрал без модели;
`fallback` — при сбое модели взят первый допустимый кандидат поиска.

## Как устроен код

```
app/
├── main.py                    # фабрика приложения, CORS, /health
├── config.py                  # настройки из окружения / .env
├── schemas.py                 # контракт API (зеркало src/types/index.ts)
├── api/                       # recommend (JSON + SSE), wardrobe, admin
├── rag/
│   ├── base.py                # порт RagEngine: sync / retrieve / validate_selection / assemble
│   ├── wardrobe_rag_engine.py # адаптер к пакету rag/ (основной режим)
│   ├── builtin_engine.py      # запасной BM25 без моделей
│   └── factory.py             # выбор движка по RAG_ENGINE
├── services/
│   ├── orchestrator.py        # пайплайн: sync → retrieve → LLM → validate → repair → fallback
│   ├── followup.py            # что пользователь хочет от последней карточки: правка, вопрос, новая тема
│   ├── editing.py             # точечная правка образа по ID и ответы на вопросы о нём
│   ├── analysis.py            # повод, якорная вещь по названию, погода (для запасного движка)
│   ├── prompts.py             # персона + правила + JSON-формат + сообщения на исправление
│   ├── validation.py          # разбор и проверка формы ответа LLM
│   ├── streaming.py           # извлечение поля "text" из потока JSON
│   ├── scoring.py             # эвристика matchScore
│   └── llm/                   # OpenAI-совместимый клиент, mock, фабрика
└── storage/app_store.py       # SQLite: настройки куратора, снимки для запасного движка
```

Промпт состоит из двух частей. **Персону** («ведущий стилист 12 STOREEZ…») куратор может менять через `PUT /api/admin/settings` (нужен `ADMIN_TOKEN`). **Правила состава и JSON-формат** зашиты в код и из админки не редактируются — иначе правкой текста можно сломать проверку. Запрос клиента и описания вещей передаются как данные; фото (`imageUrl`, в том числе base64) в промпт не попадают.

## Тесты

```bash
.venv/bin/python -m pytest          # Windows: .\.venv\Scripts\python.exe -m pytest
```

Для тестов сеть и веса моделей не нужны:

- `test_api.py` — HTTP-контракт, исправление и фолбэк LLM, SSE, синхронизация, админка (встроенный движок);
- `test_outfit_edit.py`, `test_followup.py` — точечная правка последнего образа, вопросы о нём, разбор реплик и новый вопрос после старого диалога;
- `test_wardrobe_rag_integration.py` — та же цепочка поверх **настоящих** Chroma, BM25, RRF и `validate_selection` из `rag/`; подменён только кодировщик (детерминированные тестовые векторы, как в `rag/tests`). Пропускается, если `rag/` не установлен;
- `test_openai_client.py` — протокол `/chat/completions` и разбор потока на поддельном HTTP-транспорте;
- `test_builtin_engine.py`, `test_analysis.py`, `test_validation.py`, `test_streaming.py` — модули по отдельности.

Что тестами **не** покрыто и проверяется вручную на машине показа: работа с настоящими весами моделей и ответы настоящей Qwen.

## Проверенный запуск на Mac M2 (8 ГБ)

На машине показа использовалась `qwen2.5:1.5b` (официальный GGUF Q4_K_M из
`Qwen/Qwen2.5-1.5B-Instruct-GGUF`, импорт в Ollama с `num_ctx 4096`). После
установки модели и заполнения кеша поиска интернет и внешний ключ не нужны.
Запустите Ollama, затем сервер из `backend/`:

```bash
# Терминал 1
OLLAMA_NUM_PARALLEL=1 OLLAMA_MAX_LOADED_MODELS=1 OLLAMA_CONTEXT_LENGTH=4096 ollama serve
# Терминал 2, из backend/; используйте окружение с установленным wardrobe_rag
OMP_NUM_THREADS=2 VECLIB_MAXIMUM_THREADS=2 HF_HUB_OFFLINE=1 \
  .venv-real/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

В `backend/.env`: `LLM_PROVIDER=openai`, `LLM_BASE_URL=http://127.0.0.1:11434/v1`,
`LLM_MODEL=qwen2.5:1.5b`, `LLM_API_KEY=ollama` (заглушка), `LLM_TEMPERATURE=0.2`,
`LLM_JSON_MODE=true`, `LLM_OUTFIT_SCHEMA=true`, `LLM_TIMEOUT_S=35`, `LLM_EXTRA_BODY={"max_tokens":768}`,
`RAG_ENGINE=wardrobe_rag`, `RAG_MODE=hybrid`, `RAG_OFFLINE=true`, `RAG_DEVICE=cpu`.
После успешного `/health` запустите Vite из корня с arm64 Node.js 22 и `.env.local`
из раздела выше. Для проверки: гость → «Гардероб» → «Базовая капсула» (50 вещей),
затем «Стилист» → «Деловая встреча». На существующем профиле кнопка добавляет
только недостающие вещи из капсулы, сохраняя свои вещи и правки. В финальном SSE
`result` проверьте `source: "llm"` и `meta.retriever: "wardrobe_rag"`: сама карточка
не отличает модель от фолбэка.

Перед показом закройте тяжёлые приложения и проверьте запас места под swap.
При остатке около 400 МиБ синхронизация гардероба уже завершалась ошибкой `ENOSPC`.
Первый подбор на 50 вещах сильно зависит от памяти: при давлении на swap одна
индексация заняла 152 с. Прогрейте гардероб заранее в той же сессии браузера.
Правило повода проверено для пляжа; это не общая проверка любого дресс-кода.

## Замеры на 50 вещах

```bash
# из backend/, сервер запущен с Qwen и wardrobe_rag
python scripts/bench_capsule.py --label "после" --output bench_after.json
```

Скрипт меряет три режима — первый подбор, повторный запрос и подбор после правки одной вещи —
и печатает таблицу с разбивкой на индексацию (текст / фото / запись), поиск и LLM, а также
сколько вещей закодировано заново и сколько переиспользовано.

Основная задержка на 50 вещах — индексация. Любая правка гардероба создаёт новую ревизию, и
раньше это означало растеризацию всех 50 картинок и по 50 прогонов текстовой и визуальной
моделей; при нехватке памяти одна такая индексация занимала 152 с. Теперь эмбеддинги хранятся
по содержимому (`embedding_cache.sqlite3` в `RAG_DATA_DIR`): правка одной вещи кодирует одну
вещь, а та же капсула у другого пользователя или после перезапуска сервера не кодируется вовсе.
Кеш ничего не меняет в векторах, ревизиях и ранжировании — он только пропускает работу, а файл
можно удалить в любой момент.

Чтобы снять замер «до» на той же машине, запустите сервер с `RAG_EMBEDDING_CACHE=false` и
повторите команду с `--label "до"`. Для по-настоящему холодного первого подбора укажите пустой
`RAG_DATA_DIR` и `SEED_WARDROBE_PATH=../rag/data/wardrobe_seed.json`: иначе демо-пользователь
при старте сам индексирует всю капсулу (время посева видно в логе сервера), и первый подбор
получает уже готовые векторы.

Проверка механизма без настоящих моделей (тестовый кодировщик, mock-LLM, Linux arm64, 4 ядра;
время кодирования здесь нулевое, остаётся растеризация и запись):

| Режим | Кеш выключен: индексация, закодировано | Кеш включён: индексация, закодировано |
|---|---|---|
| Первый подбор | 2679 мс, 50 текстов + 50 фото | 58 мс, 0 + 0 (векторы уже есть после посева) |
| Повторный запрос | 4 мс, ничего | 4 мс, ничего |
| После правки одной вещи | 2723 мс, 50 + 50 | 99 мс, 1 + 0 |

Эти числа показывают только, что лишняя работа исчезла. Замеры с настоящими моделями и Qwen
снимаются на машине показа той же командой.

## Чек-лист перед показом

Автопроверка на запущенном сервере (из `backend/`):

```bash
python scripts/defense_smoke.py
```

Точечная правка образа проверяется отдельной командой — десять сценариев из раздела
«Правка последнего образа»: `python scripts/edit_smoke.py`.

`defense_smoke.py` проверяет Qwen, `wardrobe_rag`, состав карточек и оба отказа
(нет обуви / нет подходящей обуви для пляжа). По умолчанию берёт 10 вещей
из капсулы, чтобы быстрее прогнать сценарии; `--full-capsule` включает все 50.
Команда выводит времена этапов и очищает только свой временный гардероб. Для показа
в браузере используйте тот же сценарий и чип «Пляж и +30°C».

1. `pip install -e ../rag` и `init-models` выполнены; в `.env` — `RAG_ENGINE=wardrobe_rag`, `RAG_OFFLINE=true`.
2. `/health` показывает `"engine": "wardrobe_rag"` и нужную модель LLM.
3. Запрос «Москва: +6°C, ветрено, деловая встреча» с `"debug": true` и массивом `wardrobe` из [`wardrobe_demo_weather.json`](../rag/data/wardrobe_demo_weather.json): есть верхняя одежда, `source: "llm"`. Для вещей без погодных атрибутов возможны предупреждения.
4. Гардероб из [`wardrobe_demo_missing_shoes.json`](../rag/data/wardrobe_demo_missing_shoes.json) → `missingSlots: ["shoes"]`, карточки нет.
5. В браузере спросите «С чем носить широкие брюки?» — ожидается `source: "llm"` без `meta.retriever` и карточки. Затем подберите образ и спросите «А можно потеплее?» без указания погоды: стилист уточнит температуру, не меняя карточку. После ответа, например «+6°C», он предложит обоснованную правку или объяснит, почему подходящего варианта нет.
6. Остановите Ollama и повторите запрос с полным гардеробом: ожидается `source: "fallback"`. Отключение интернета само по себе не отключает локальную Ollama.
